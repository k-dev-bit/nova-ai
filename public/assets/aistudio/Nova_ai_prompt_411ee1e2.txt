Build a complete, functional, local-first, multimodal personal AI assistant named Nova AI for Web, PWA, and Android APK.

You are a senior full-stack developer, Android engineer, AI systems architect, security engineer, and UI/UX designer. Implement a real application, not just a UI mockup. Create the source files, connect functional services, test the application, and fix errors.

Provider identification workflow

1. Accept the key only after an explicit user action.
2. Inspect recognizable provider-specific prefixes only as hints, never as definitive proof.
3. Ask the user to select a provider if identification is uncertain.
4. Validate the key through the selected provider's documented API.
5. Discover available models through supported endpoints.
6. Determine available capabilities from documented metadata and verified model information.
7. Let the user confirm the configuration.
8. Store the credential using the platform's secure storage mechanism.

Do not try every provider with a secret key indiscriminately. Never send a credential to an endpoint unless the endpoint is known to belong to the selected provider.

Some APIs do not support model discovery or capability queries. For those providers, allow manual model entry and explain the limitation.

Do not display secret keys in logs, URLs, analytics, error reports, or UI after saving.

4.4 Auto Mode

Create a prominent mode selector:

- Auto Mode.
- Manual Mode.

In Auto Mode, Nova chooses the most appropriate enabled and configured provider for each task.

Examples:

User: "Explain photosynthesis."

Choose a configured text model suitable for general conversation.

User: "Write a complex React application."

Prefer a configured model with strong coding capabilities, based on explicit capability metadata, user priorities, and measured performance where available.

User: "Generate an image of a futuristic city."

Choose an enabled image-generation provider that supports image generation.

User: "Analyze this photograph."

Choose a model that supports image understanding.

User: "Talk to me continuously in Hindi."

Choose a compatible real-time audio model or a configured speech-recognition, text-generation, and speech-synthesis pipeline.

User: "Summarize this long document."

Choose a compatible model with sufficient context capacity.

Auto Router algorithm

Implement a task router that:

1. Classifies the request into a task type.
2. Identifies required capabilities.
3. Filters providers that are disabled, unconfigured, incompatible, or unavailable.
4. Considers user-defined priority, capability support, latency, rate limits, estimated cost, and context capacity when reliable information is available.
5. Selects the best eligible provider and model.
6. Executes the request using the correct adapter.
7. Records non-sensitive routing metadata locally.
8. Displays which provider and model handled the request.

Do not invent real-time speed rankings, quality scores, pricing, or benchmark results.

If performance statistics are available, derive estimates from actual observations. Otherwise, use explicit user priorities and configured model capabilities.

If multiple models are equally suitable, use a predictable selection rule.

If no eligible provider exists, ask the user to configure one.

Auto Mode failure handling

If a request fails:

- Explain the failure.
- Distinguish authentication, quota, network, and model errors.
- Retry transient failures within reasonable limits.
- Consider an alternative provider only in Auto Mode and only if allowed by user settings.
- Never switch providers silently when that would violate privacy or cost preferences.
- Never retry invalid credentials indefinitely.

Provide a setting to allow or disable automatic fallback.

Default to transparent provider selection and conservative cost controls.

5. API SECURITY

API keys are secrets.

For the browser application:

- Never hardcode real API keys.
- Never expose keys through VITE_ or other public frontend environment variables.
- Never store plaintext keys in localStorage or ordinary IndexedDB records.
- Use Web Crypto encryption with an explicit user-controlled passphrase or another carefully designed browser-side protection mechanism.
- Do not claim that client-side encryption fully protects secrets from malicious code running in the same browser origin.
- Provide an app-lock or credential-lock feature.
- Clear decrypted credentials from memory when practical.

For Android:

- Use Android Keystore-backed encryption.
- Keep encrypted credentials in private app storage.
- Never log credentials.
- Exclude secrets from exported backups.

Prefer direct-to-provider requests when a provider explicitly supports browser clients and the security implications are clearly explained.

If a provider requires a protected server-side secret or browser access is blocked by CORS, provide an optional, separately configured backend proxy. Never put a server secret into frontend code.

Use the minimum permissions necessary.

11. SMART CONTACT MEMORY AND CALLING

Implement a dedicated Android voice-command service for contact search and phone calling.

Example commands:

- "Papa ko call karo."
- "Bhaiya ko phone lagao."
- "Mummy ko call karo."
- "Call my father."
- "Papa ko video call karo."

Contact resolution order

1. Search user-approved saved contact memory.
2. Search Android contacts when permission is granted.
3. If multiple matches exist, ask the user to choose.
4. If no match exists, ask the user for the phone number.
5. Confirm the contact and number before saving or dialing, especially when ambiguity exists.
6. Open the Android dialer with the resolved number, or place a direct call only if the user has explicitly enabled that behavior and the platform permits it.

For example:

User: "Papa ko call karo."

Nova searches saved memory first. If a number is found, it presents the resolved contact and starts the configured call workflow.

If memory has no match, Nova searches Android contacts.

If neither has a match, Nova asks: "Papa ka phone number kya hai?"

After the user provides the number, Nova may offer to save the contact to local memory and open the dialer.

Requirements

- Support aliases such as Papa, Pappa, Father, Bhaiya, Brother, Mummy, and user-defined nicknames.
- Allow user-created contacts stored in local memory.
- Allow edit, delete, and search.
- Do not merge unrelated people just because their names are similar.
- Request Android contacts permission only when necessary.
- Avoid uploading the address book to an AI provider.
- Use Android intents or documented native APIs.
- Do not pretend a call was placed if only the dialer was opened.

For normal cellular calls, use the supported Android dialer integration.

For video calls, open the relevant app or supported contact action only when a compatible application is available.

Do not secretly record cellular calls.
